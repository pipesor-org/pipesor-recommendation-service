# Repository instructions

## Context by task

- Before implementation, read the [common backend conventions](https://github.com/pipesor-org/pipesor-docs/blob/main/docs/development/backend-conventions.md) and [Java/Spring conventions](https://github.com/pipesor-org/pipesor-docs/blob/main/docs/development/java-spring-conventions.md). Use the accessible pipesor-docs checkout when available, distinguishing local changes from integrated main. Apply only the conventions relevant to this service; they do not add tables, integrations or permissions.
- Use [README.md](README.md#development-and-verification) for setup, runnable commands and contribution policies. Add verified commands there when introducing application tooling; reference them rather than maintaining a second command list here.
- For diagnostic orchestration, output composition or human-review changes, consult [architecture](docs/architecture.md) and its current model/ADRs. Read ADR-015/017 for internal responsibilities and ADR-016 together with ADR-019 for current caller, identity and artifact-publication boundaries. Follow references for the affected subject, not the entire documentation set for every edit.
- For dependency selection, inference access, persistence or delivery work, consult the relevant sections of the [deployment contract](docs/deployment-contract.md). Its development baseline records the authorized version-selection policy; its integration and data sections identify owned records and unresolved access requirements.
- Treat local architecture summaries as navigation, not frozen specifications. Use the accessible `../../pipesor-docs/` checkout or linked sources on `main`, accounting for later accepted decisions and relevant uncommitted changes. Inspect uncommitted source changes separately; their presence does not establish integration or approval. Report unavailable or conflicting evidence when it affects the task. Documentation links must follow `main` across repositories and relative paths within this repository; a consulted revision may be recorded as text only.

## Implementation constraints

- Keep Diagnostic API, orchestration, output composition and human review within this service. Preserve the synchronous correlated-context-to-RAG-to-inference flow without introducing additional services, direct vector-store access or a separate response relationship for a normal HTTP reply. Component projections describe internal responsibilities, not extra deployments or duplicated calls.
- Send only sanitized evidence and authorized contextual knowledge to inference. Preserve execution identity, `correlationId`, evidence links and source provenance through output and persistence. Validate provider output against the agreed diagnostic contract; do not present unsupported model claims, invented citations or missing evidence as established facts.
- Compose probable causes, recommendations and limitations rather than guaranteed diagnoses. Do not impose a confidence scale such as 0..1 (PD-004), invent risk categories/thresholds (PD-009), or treat model confidence as human approval. Preserve the required reviewer, decision, diagnostic identity, timestamp and correlation trace under the agreed review contract. Recommendations must not trigger autonomous remediation.
- Confine writes to owned diagnosis, recommendation, evidence/source-link and human-review records. Preserve logical references without cross-schema foreign keys or cross-context ORM navigation. Do not modify upstream evidence, pipeline state or RAG knowledge, or add cross-context reads/joins to fill the unresolved query-reconstruction contract (PD-011).
- Produce the diagnostic output/artifact content; GitHub Actions publishes its own artifact. Do not upload artifacts or mutate workflows through the read-only GitHub App. Authorize dashboard queries, review operations and workflow access according to their respective contracts; dashboard identity and GitHub App authentication do not resolve PD-036's workflow authorization.
- The Foundry foundation does not establish a compatible application endpoint/SDK, model availability or grants. Do not select the concrete LLM variant while PD-026 remains intentionally open, or introduce model hosting/training to complete inference. The general latest-compatible dependency policy does not override this model-selection boundary.
- Check input validation, RAG/inference failures, persistence and output/review behavior together when changing orchestration. Use agreed error, retry and compatibility contracts; do not fabricate successful diagnoses when dependencies fail or assume retried requests can duplicate reviews or diagnoses harmlessly.
- A request to implement a local increment authorizes its required local code, tooling and checks. Do not create cloud resources, permissions or secrets, or modify neighboring repositories as a side effect. Keep credentials and sensitive evidence out of committed files and reported output.
- Identify the specific missing agreement and its impact when an increment depends on confidence/risk semantics, context reception, query reconstruction, model selection or caller authorization. Continue independent scaffolding and isolated behavior work; do not invent the missing contract or block the whole service over unrelated decisions.

## Verification and handoff

Use the applicable checks documented in the README. Add behavior checks with the first executable increment, including material cases for malformed inference output, unsupported evidence/source links, RAG/provider failure, unauthorized review and preservation of human decisions and correlation context. Use synthetic sanitized evidence and mocked dependencies; these tests do not establish diagnostic accuracy or live-provider compatibility. Live database, RAG, provider or workflow checks need their own agreed scope and access.

For documentation-only edits, check affected links and source coherence; parse TOML when changing agent configuration. Do not claim a build or integration passed before it exists and has run. Keep the documentation that owns a changed behavior or command current in the same change. Report what changed, checks actually performed and remaining blockers. For substantial work spanning sessions, keep a task-specific plan with scope, acceptance criteria and verification progress; a small edit needs no plan file.

When a focused review is warranted and delegation is authorized, `diagnostic_reviewer` checks evidence-backed probable-cause output, limitations, human control, diagnosis ownership and orchestration boundaries. Supply the task and affected paths. Its review supplements the main agent's verification and human review.
